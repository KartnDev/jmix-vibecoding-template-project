# Вайб-кодинг на Jmix: как это работает

Первую неделю я выбросил 70% сгенерированного кода. LLM путали версии Jmix, изобретали несуществующие API, использовали EntityManager вместо DataManager. Вторую неделю — выбросил 20%. Третью — почти ничего.

Разница — в настройке. Эта статья о том, как её сделать правильно.

До вайб-кодинга я тратил три дня на CRUD для справочников. Формы, таблицы, валидация — рутина, которую делал сотни раз. Потом попробовал по-новому — и первый экран был готов за 15 минут. К вечеру был работающий модуль с пятью сущностями, экранами и ролями.

Jmix даёт то, чего не даёт "просто Spring": авторизация, роли, аудит, CRUD, UI — из коробки. Фреймворк строгий, есть правильный способ делать вещи. AI-у сложнее накосячить когда правила чёткие. Ты получаешь приложение с готовым UI и безопасностью — а не REST API, который потом месяц обвешивать фронтендом.


## Проблема: "готово" не значит "работает"

LLM любят говорить "готово" когда код компилируется. Компиляция — это четверть успеха.

В Jmix ошибки распределяются примерно так:

- **Compile time** (~25%) — забыл импорт, опечатался в типе. LLM справляются.
- **Design time** (~25%) — приложение не стартует: Spring не поднялся, Liquibase упал. LLM справляются, если попросить запустить.
- **Runtime** (~50%) — открыл экран — ошибка. Нажал кнопку — ничего. Сохранил сущность — данные не те. Здесь живёт большинство проблем.

Типичный сценарий: LLM написал view, код скомпилировался, приложение запустилось. "Готово!" Открываешь экран — NullPointerException. Или кнопка не работает. Или данные не сохраняются. Начинается цикл: тестируешь, объясняешь, LLM фиксит, снова тестируешь...

Вся скорость уходит в этот цикл. Чтобы его разорвать — нужно дать LLM инструменты для самопроверки. Но сначала разберёмся, какие модели вообще понимают Jmix.


## Модели: кто знает Jmix

Не все LLM одинаково полезны.

**Топовые** (Claude Opus, Gemini Pro) — знают Jmix 2.x, понимают Vaadin Flow, редко галлюцинируют. Можно работать почти без контекста.

**Средние** (Claude Sonnet, GPT-4/5, Gemini Flash) — знают базу, но додумывают. Могут использовать `@GeneratedValue` вместо `@JmixGeneratedValue` или забыть про `@InstanceName`. С хорошим контекстом — нормально.

**Дешёвые и локальные** — много галлюцинаций. Код выглядит правильно, но не работает.

Вот конкретный пример. Промпт: "создай entity Customer с полями name, email":

```
Opus:  @JmixEntity + @Entity + UUID + @Version + @InstanceName → работает
GPT:   @Entity + @GeneratedValue (без @JmixEntity) → компилируется, не работает
```

Почему GPT-версия не работает? Jmix не видит сущность без `@JmixEntity` — она не появится в UI, DataManager её не найдёт, Studio не сгенерирует экраны. Код компилируется, приложение стартует, но сущности как будто нет. Классическая runtime-ошибка, которую ловишь через час отладки.

Контекстные файлы нужны всем моделям — топовым помогают избегать таких ошибок, слабым позволяют работать вообще. Но модель — это только половина. Вторая — где её запускать.


## Платформы: где запускать модель

Главный совет: используй то, за что уже платишь.

| Платформа | Для кого | Плюсы | Минусы | Цена |
|-----------|----------|-------|--------|------|
| **Cursor** | VS Code | Лучший контекст — сам подхватывает правила | Нет интеграции с Jmix Studio | ~$20/мес |
| **Claude Code** | Любой редактор | Opus без лимитов, работает в терминале | Иногда "забывает" правила в длинных сессиях | $20/мес |
| **Junie** | IntelliJ IDEA | Нативная интеграция, видит структуру проекта | Не проактивный — делает только то, что просишь | По потреблению |
| **Continue** | Локальные модели | Бесплатно, данные не уходят наружу | Для Jmix — много галлюцинаций | Бесплатно |

Я пробовал все. Остановился на Claude Code — Opus понимает Jmix лучше других, терминальный агент удобен для итераций. Для чувствительных проектов — Continue с локальной моделью, но там приходится больше контролировать.

Платформа даёт модель и контекст. Но помнишь цикл "открыл экран — ошибка — объясняешь — фикс"? Платформа его не решает. Для этого нужен другой инструмент.


## MCP: руки для агента

MCP (Model Context Protocol) — способ дать AI доступ к инструментам. Из коробки LLM умеет только генерировать текст. MCP позволяет ему проверять ошибки в IDE, открывать браузер, запускать команды.

Для Jmix нужны два MCP-сервера:

**IDEA MCP** — подключает агента к IntelliJ IDEA. Не просто ошибки компиляции, а предупреждения Jmix Studio: непереведённые сообщения, несуществующие компоненты в XML, проблемы с fetch plans. То, что компилятор пропустит, а Studio поймает.

**Playwright MCP** — даёт агенту браузер. Он сам открывает localhost:8080, логинится, кликает по экранам, видит что кнопка не работает или данные не сохраняются.

Разница на практике:

```
БЕЗ MCP:                           С MCP:
1. Агент написал view              1. Агент написал view
2. Скомпилировалось — "готово!"    2. Проверил IDEA MCP — нашёл варнинги — пофиксил
3. Ты открываешь — ошибка          3. Открыл Playwright — потыкал — нашёл баг — пофиксил
4. Объясняешь что не так           4. Тебе отдал работающий код
5. Агент фиксит
6. Повторяешь 3-5
```

Когда я первый раз увидел как Playwright сам нашёл баг в форме — я понял что это работает. Большинство runtime-ошибок теперь находит агент.

### Установка MCP

**IDEA MCP (для IntelliJ IDEA):**
1. File → Settings → Tools → AI Coding Assistants → MCP Servers
2. Добавить конфигурацию (IDE обычно предлагает встроенный сервер)
3. Или установить плагин "MCP Server" из Marketplace

**Playwright MCP (для Claude Code):**
```bash
# В настройках Claude Code (~/.claude/settings.json или через UI):
# Добавить MCP server с командой:
npx @anthropic/mcp-server-playwright
```

После настройки агент получает инструменты `browser_navigate`, `browser_click`, `browser_screenshot` — и может сам тестировать UI.

**Важно:** Playwright медленный — 30-60 секунд на цикл. Для быстрых итераций я часто проверяю сам, Playwright — для финальной верификации перед коммитом.

---

**Хочешь попробовать прямо сейчас?** Склонируй [jmix-vibecoding-template-project](https://github.com/jmix-framework/jmix-vibecoding-template-project), запусти `./gradlew bootRun`. MCP настроишь потом — сначала посмотри как работает базовый вайб-кодинг.

## Сетап: минимум, который работает

Не нужно создавать 15 папок с "агентами" и "verification cycles". На практике используется малая часть.

### AI-README

Один файл с контекстом. Какой — зависит от платформы:

| Платформа | Файл |
|-----------|------|
| Claude Code | `CLAUDE.md` |
| Cursor | `.cursorrules` |
| Junie | `.junie/guidelines.md` |
| Несколько платформ | `AGENTS.md` |

Минимальный CLAUDE.md:

```markdown
# Project: Jmix 2.x Application

## Stack
- Java 17, Spring Boot, Vaadin Flow
- Database: HSQLDB (dev), PostgreSQL (prod)
- Run: `./gradlew bootRun` (localhost:8080, admin/admin)

## Rules
- Entity: @JmixEntity + UUID (@JmixGeneratedValue) + @Version + @InstanceName
- Data access: DataManager only (NOT EntityManager)
- DI: constructor injection (no field @Autowired)
- Views: XML descriptor + Java controller pair
- All UI text: msg:// keys, add to ALL locale files

## Forbidden
- Lombok on entities
- Business logic in views
- Edits in frontend/generated/
```

Модель знает что это за проект, какие правила, чего делать нельзя. Этого достаточно для старта.

### Промпт

Не нужно писать поэму. Рабочая структура:

```
Изучи проект — посмотри CLAUDE.md, структуру, существующие entity и view.

Создай entity Order с полями:
- customer (связь с Customer)
- date (дата заказа)
- total (сумма)
- status (enum: NEW, PROCESSING, DONE)

Создай list view и detail view для Order.
Добавь в меню после Customers.
Напиши unit-тест для OrderService.

После каждого изменения — проверь через IDEA MCP (get_file_problems).
Когда view готов — открой в браузере через Playwright и проверь:
- Список отображается
- Создание работает
- Редактирование сохраняет данные

Работающий кусок — коммить с понятным сообщением.
```

Обрати внимание на "напиши unit-тест". AI отлично пишет тесты — используй это. Тесты ловят регрессии когда AI меняет код в следующих итерациях.


## Когда это не работает

Честности ради — вайб-кодинг не решает всё.

**Сложная бизнес-логика** — AI хорош в CRUD и типовых операциях. Нетривиальные расчёты, сложные state machines, специфичные алгоритмы — лучше писать самому.

**Интеграции с внешними системами** — AI не знает твой конкретный API. Придётся много объяснять и проверять.

**Legacy без тестов** — AI добавит хаоса. Сначала покрой критичные места тестами.

**Команда из джуниоров без присмотра** — AI усиливает и плохое тоже. Если человек не понимает код который копирует — баги будут в проде. Обязательный код-ревью для AI-сгенерированного кода.

**Чувствительные данные** — код уходит в облако. Для проектов с NDA или персональными данными — либо локальные модели, либо чистить контекст от секретов.

Но для типовых задач — CRUD, админки, прототипы, внутренние инструменты — вайб-кодинг работает. И работает быстро.


## Итого

AI пишет код быстрее тебя. Jmix даёт структуру, в которой сложно накосячить. MCP позволяет агенту самому находить ошибки. Вместе — рабочая комбинация.

Сетап занимает час. Первая entity — 15 минут. К концу дня — работающий прототип с несколькими сущностями, экранами, ролями и валидацией. Не "полноценная CRM", но основа, которую можно показать и развивать.

Минимальный набор:
- AI-README с правилами проекта
- IDEA MCP для проверки ошибок
- Playwright для тестирования UI

Начни с этого. Столкнёшься с проблемой — добавишь решение.
